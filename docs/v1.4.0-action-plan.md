# Hammerspace CSI v1.4.0 Action Plan

## Release objective

Hammerspace CSI v1.4.0 should be a production-hardening and Kubernetes-operability
release, with PVC cloning as its headline feature.

The release should prioritize security, correctness, recovery, CSI conformance,
packaging, and automated quality gates. VolumeGroupSnapshots, health APIs, SMB,
and a full operator should follow after these foundations are stable.

## Required v1.4.0 scope

| Workstream | Required outcome |
| --- | --- |
| Security | TLS verification by default, CA bundle support, and secret-safe logs |
| Reliability | Resolve confirmed Critical/High findings and dangerous error paths |
| Recovery | Persistent freeze recovery and backend-authoritative idempotency |
| Controller HA | Two replicas with driver-level leader election |
| CSI correctness | Fix expansion, capacity, capability, list, staging, readonly, and response issues |
| Competitive feature | PVC-to-PVC cloning |
| Kubernetes integration | Current CSI spec and sidecars, RWOP, and explicit filesystem policy |
| Packaging | Production Helm chart |
| Quality | Modern CSI sanity, race tests, fault tests, and an E2E matrix |
| Supply chain | Trivy, SBOM, image signing, and pinned build dependencies |

## Milestone 0: Baseline and scope freeze

- Tag or branch the exact v1.3.0 baseline.
- Catalogue all 32 adversarial-review findings.
- Classify each finding as Confirmed, Already fixed, Needs reproduction, or Rejected.
- Define the supported Kubernetes, Hammerspace/Anvil, Rocky Linux, NFS, and
  filesystem compatibility matrix.
- Define upgrade and rollback compatibility with v1.3.0.
- Decide the future of legacy CSI v0 support. The recommendation is to deprecate
  it in v1.4.0 and remove it in a later major release.

## Milestone 1: Security and correctness blockers

### TLS and credentials

- Enable TLS certificate verification by default.
- Add an `HS_CA_BUNDLE` or equivalent CA-file setting.
- Support mounting the CA through a Kubernetes Secret or ConfigMap.
- Emit a prominent warning when verification is explicitly disabled.
- Never serialize CSI request messages containing `Secrets` into logs.
- Document least-privilege Anvil credentials.
- Test trusted certificates, custom CAs, invalid certificates, and the explicit
  insecure compatibility mode.

This default change requires an upgrade note because installations using
self-signed certificates may otherwise stop connecting.

### Controller and client correctness

- Retain regression coverage for the already-fixed snapshot-map race (C-1).
- Retain regression coverage for the already-fixed HTTP 400 false-success path (H-5).
- Rebuild HTTP requests after authentication retries, close discarded responses,
  and serialize login (M-4).
- Propagate volume-existence and snapshot-list failures (M-7).
- Eliminate `os.Exit` calls from library code (L-2).
- Retain the empty snapshot-response guard (L-3).
- Stop treating every HTTP 500 response as "file not found" (L-11).

### Mount correctness

- Hold a backing-mount reference throughout NFS directory creation (H-3).
- Canonicalize backing-share keys and correctly release file/directory-backed
  mounts (H-4).
- Key mount attempts by target, source, and options so portal fallback works (M-3).
- Serialize stage/unstage and fail closed on marker-read failures (M-5).
- Replace mount probes that can leak blocked goroutines with
  `/proc/self/mountinfo`-based checks (M-6).
- Correct loop-device cleanup after partial failure (L-13).
- Reconcile controller-side root-export mounts (L-14).

## Milestone 2: Crash recovery and controller availability

### Snapshot freeze recovery

- Persist each successfully frozen target before starting the backend snapshot.
- Store recovery records under a durable host path such as
  `/var/lib/hammerspace-csi/frozen`.
- Remove a record only after a successful unfreeze.
- Reconcile and unfreeze recorded targets during driver startup.
- Add a maximum freeze-window watchdog.
- Expose metrics for frozen targets, freeze duration, recovery attempts, and
  failed unfreezes.
- Test controller termination between freeze and snapshot completion.

### Volume and snapshot idempotency

- Find snapshots through deterministic backend metadata or naming.
- Confirm source-volume identity before returning an existing snapshot.
- Persist operation state through Hammerspace metadata where possible.
- Create file-backed volumes with temporary names, format them, and then
  atomically rename or mark them complete.
- Reconcile incomplete volume and snapshot operations during startup.
- Add bounded TTL cleanup for any remaining local caches.

### Controller high availability

- Run two controller replicas.
- Implement driver-level Kubernetes Lease leader election.
- Allow only the leader to serve mutating controller RPCs.
- Ensure non-leaders return retryable statuses or do not expose the controller
  service.
- Enable leader election on applicable CSI sidecars.
- Add a PodDisruptionBudget and pod anti-affinity.
- Test leader termination during create, delete, expand, clone, and snapshot
  operations.

Sidecar leader election alone is insufficient because the CSI driver owns mutable
operation state.

## Milestone 3: CSI and Kubernetes correctness

### Expansion

- Lock expansion using the canonical volume ID.
- Compare requested size with the configured size limit, not free capacity.
- Never shrink a share.
- Prefer a narrow backend size update over a raw GET-modify-PUT operation.
- Return a valid response for NFS node-expansion no-ops.
- Require and validate `VolumeCapability`.
- Grow XFS through the mounted filesystem path.
- Grow ext4 through the correct loop-device and mount flow.
- Resize raw block backing files/devices without filesystem operations.
- Verify the resulting capacity before reporting success.
- Test online and offline expansion for every supported volume type.

### CSI conformance

- Treat an empty filesystem type as default NFS in `GetCapacity` (M-8).
- Validate capabilities from actual volume identity instead of absent
  StorageClass parameters (M-9).
- Correct `ListVolumes` IDs and implement pagination (L-5).
- Return backend-derived snapshot readiness and timestamps (L-6).
- Honor `staging_target_path`, or explicitly redesign and document staging (L-7).
- Enforce readonly NFS publication (L-8).
- Remove the advertised `RPC_UNKNOWN` capability (L-9).
- Correct environment validation (L-10).

### Kubernetes integration

- Set `attachRequired: false`.
- Remove the `csi-attacher` sidecar.
- Set an explicit `fsGroupPolicy`.
- Add RWOP support where the volume semantics permit it.
- Evaluate `seLinuxMount: true` with OpenShift/SELinux testing.
- Retain `storageCapacity: true` only after `GetCapacity` is corrected.

### Dependency modernization

- Upgrade from CSI spec v1.9 to the selected supported current version.
- Upgrade CSI sidecars as a tested compatibility set.
- Upgrade `csi-test`.
- Pin released image versions and digests.
- Do not independently select untested "latest" sidecar versions.

## Milestone 4: PVC-to-PVC cloning

Implement `VolumeContentSource_Volume` for:

- Share-backed NFS volumes.
- NFS directory-backed volumes.
- File-backed ext4 volumes.
- File-backed XFS volumes.
- Raw block volumes.

Suggested workflow:

```text
Source PVC
  -> identify backing type
  -> create temporary backend snapshot
  -> restore or clone into the destination
  -> validate the destination
  -> remove the temporary snapshot
  -> return an idempotent CreateVolume response
```

Requirements:

- Advertise `CLONE_VOLUME`.
- Never permit a destination smaller than its source.
- Reject incompatible source and destination volume modes.
- Handle retries without creating duplicate backend objects.
- Preserve requested objectives and metadata.
- Clean up after partial failures.
- Test clones while source volumes are mounted.
- Document whether each clone type is metadata-fast or performs a full copy.

## Milestone 5: Helm packaging and operations

Ship a production Helm chart containing:

- Controller Deployment and node DaemonSet.
- RBAC and `CSIDriver` resources.
- StorageClass and VolumeSnapshotClass templates.
- Service and optional ServiceMonitor resources.
- PodDisruptionBudget and leader-election configuration.
- Security contexts and required host mounts.
- TLS CA and credential references.
- OpenTelemetry and Prometheus configuration.
- Kubernetes-version-specific feature settings.
- Configurable image registry, tag, and digest.

Packaging quality requirements:

- `values.schema.json`.
- `helm lint` and rendered-template tests.
- Upgrade tests from the v1.3 raw manifests.
- Air-gapped registry support.
- Hardened example values.
- OpenShift/SCC documentation and validation.

A full operator should not block v1.4.0. Helm provides most of the immediate
operational value with substantially less release risk.

## Milestone 6: Automated quality gates

Required CI flow:

```text
Formatting and static analysis
  -> unit tests
  -> go test -race
  -> mock-Anvil integration tests
  -> modern csi-sanity
  -> Kubernetes E2E
  -> image build
  -> Trivy
  -> SBOM
  -> image signing
```

Fault-injection coverage:

- Controller killed during freeze.
- Controller killed during formatting.
- Leader failover during snapshot operations.
- Anvil returns 400, 401, 403, 500, or malformed JSON.
- An NFS portal hangs during mount.
- A backing mount disappears during directory creation.
- Concurrent publish/unpublish and stage/unstage.
- Expansion racing with deletion.
- Duplicate CreateVolume and CreateSnapshot requests.

E2E coverage matrix:

| Volume mode | Create/Delete | Snapshot/Restore | Clone | Expand | Restart |
| --- | ---: | ---: | ---: | ---: | ---: |
| Share-backed NFS | Yes | Yes | Yes | Yes | Yes |
| NFS directory-backed | Yes | Yes | Yes | Yes | Yes |
| File-backed ext4 | Yes | Yes | Yes | Yes | Yes |
| File-backed XFS | Yes | Yes | Yes | Yes | Yes |
| Raw block | Yes | Yes | Yes | Yes | Yes |

## Milestone 7: Release and supply-chain qualification

- Require no fixable HIGH or CRITICAL Trivy findings.
- Produce an SPDX or CycloneDX SBOM.
- Sign the release image with Cosign.
- Generate build provenance or attestations.
- Pin the base image by digest.
- Publish checksums and release notes.
- Test v1.3.0 to v1.4.0 upgrades.
- Test rollback to the previous driver version.
- Verify existing PVC availability throughout an upgrade.
- Document default changes, especially TLS and `attachRequired`.
- Run release candidates through performance, scale, failover, upgrade, and
  rollback qualification before GA.

## Stretch goal: VolumeAttributesClass

VolumeAttributesClass support may enter v1.4.0 only after all required milestones
are stable. Candidate mutable attributes include:

- Objectives.
- Tier or placement policy.
- Protection policy.
- Performance policy.
- Metadata tags.

Mutable per-volume policy could become a strong Hammerspace differentiator, but it
must not delay security, recovery, cloning, packaging, or conformance work.

## v1.4.0 release exit criteria

v1.4.0 is ready for general availability only when:

- Every confirmed Critical and High finding is closed or formally accepted.
- No known false-success data-integrity path remains.
- A controller restart cannot leave a workload filesystem permanently frozen.
- Two-controller failover passes E2E qualification.
- PVC cloning works for every supported volume mode.
- CSI sanity passes against the selected CSI version.
- Upgrade and rollback tests pass.
- Helm install, upgrade, and uninstall tests pass.
- Trivy reports no fixable HIGH or CRITICAL vulnerabilities.
- SBOM, signatures, provenance, release notes, and migration documentation are
  published.
